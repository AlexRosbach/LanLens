# VMware vSphere discovery (#142)

Enable Advanced View, open Settings → Inventory tools → VMware vSphere / vCenter, enable the integration and save a vCenter HTTPS origin plus a read-only service account. Test connection, then Discover devices. The account needs read access (System.Read and visibility to the relevant hosts and VMs); no guest credentials or VM control privileges are required. Use the system trust store or mount a combined CA bundle read-only and set SSL_CERT_FILE. Certificate and hostname verification are enabled by default. Prefer trusting the issuing internal CA. Administrators may explicitly disable certificate verification for this endpoint only (also applies to connection testing and VI/JSON); this exposes credentials and inventory to potential interception. DNS pinning and HTTPS remain required. The Features tab exposes the same integration switch as Inventory tools; disabling it blocks discovery/test requests without deleting credentials or observations. Passwords use the existing Fernet credential encryption and are not returned by the API. Changing the origin or username clears the stored password.

This first implementation targets vCenter 7+ REST (/api/session, /api/vcenter/host, /api/vcenter/vm, per-VM details and guest network interfaces). No PowerCLI or extra runtime package is required. Standalone ESXi, scheduling, multiple vCenter instances and environments exceeding 100 hosts / 500 VMs are follow-up scope. Discovery is manual and bounded; a failed inventory request does not overwrite the last snapshot. Guest IP availability depends on VMware Tools and permissions. Powered-off VMs may still have hardware MAC addresses. A power state does not establish network reachability.

Existing devices are matched in order by real MAC, unique guest IP and exact case-insensitive VM name/hostname. Prior VM instance UUID associations protect against duplicates when hardware changes. Conflicting identifiers or ambiguous candidates remain inventory-only. A scanner-generated IP-only identifier may be upgraded to a verified hardware MAC, but real MACs and operator data are not overwritten. Unmatched VMs with non-conflicting real MACs are created as unregistered devices. Hosts are listed even if not yet present in LanLens; exact existing hostname/IP matches allow host/VM relationships. No synthetic MACs are generated, and no upstream VM changes or device deletions are performed by discovery. Previously observed objects not seen during a later discovery are marked stale. Device data and manual relationships are preserved. Select a linked inventory name to open the device detail.

API reference: https://developer.broadcom.com/xapis/vsphere-automation-api/latest/

A manual discovery uses a 90-second collection timeout (plus session cleanup), below the default reverse-proxy API timeout. Large or slow inventories can require a later batched/background discovery implementation.


## Extended inventory and mapping (#143)

Datacenter and cluster inventories are collected via filtered vCenter REST queries. Host placement links VMs to their clusters and datacenters when unambiguous; missing or conflicting membership is left unknown. Powered-off and suspended VMs remain visible, regardless of guest network availability. Inventory columns are individually selectable, with safe defaults and a reset option. Identity data remains collected for matching. Disabling virtual disks skips the extra disk enrichment request.

REST VM details provide disk labels, capacity and backing paths. On vCenter 8.0 Update 1 or newer, the read-only Virtual Infrastructure JSON API (VI/JSON) additionally provides backing UUIDs through a separate short-lived session, using the same validated HTTPS transport. vCenter 7 and inaccessible VI/JSON endpoints still yield REST disk metadata; missing UUIDs remain unknown and discovery reports a warning. Disk records are keyed by VM-scoped hardware key, not UUID alone. No guest disk serials or filesystem UUIDs are inferred. See https://developer.broadcom.com/xapis/virtual-infrastructure-json-api/latest/.

In Settings → CMDB, the optional i-doit mapping sources include VM instance/BIOS UUID, vCenter instance UUID, host, cluster, datacenter, VM power state, disk UUIDs and disk inventory. Targets are blank by default; use the existing mapping editor and dry-run preview to choose and validate compatible categories before synchronization. Only an unambiguous, currently matched VM from an enabled connection contributes values. Unknown/stale values are skipped; disk UUIDs are informational and never replace existing device identity or drive matching. Custom VMware attributes/tags and SOAP disk UUID support for older vCenter versions are follow-ups. Live verification requires a real vCenter and i-doit environment.

## Optional i-doit SYS-ID custom attribute writeback

Enable VMware in Settings → Features → Extensions and save changes. Its configuration appears in Inventory tools only while the feature is enabled. Configure and save the connection, then select a VM-compatible custom attribute by its field key in Inventory tools. Writeback is opt-in; upgrades from annotation writeback disable it until a field is selected. Existing VM notes are never modified by the sync. Different existing custom attribute values are protected. vCenter 8.0 Update 1+ and permission to set the selected custom attribute are required.

## Device observations and inbound custom attributes

Configuration is under the dedicated Deep Scan settings page (`/deep-scan-settings`), VMware tab, when the VMware feature is enabled. Linked VMware inventory appears under the device's Deep Scan VMware tab; passive Discovery remains independent. Hardware is also shown in the Hardware tab and as a dashboard fallback when guest inventory is missing. No SSH/WinRM credentials are required for these observations. Existing guest observations are kept separately. VMware vCPU counts and provisioned memory are not physical hardware measurements.

Select a VM custom attribute and optionally enable inbound SYSID import. Import requires a unique current VM with a matching MAC and instance UUID, a unique syntactically valid SYSID and an empty local SYSID/object link. Conflicts never overwrite existing values. Selected custom attributes can also be mapped to named, read-only device fields. Only explicitly selected attributes are collected, and attribute values are not emitted to diagnostic logs. Attribute reading uses the vCenter VI/JSON API (8.0 Update 1 or newer); older versions may lack this functionality. Hardware/attribute observations refresh on VMware discovery.

Use Load VM attributes to fetch field definitions, select the desired attributes, save and run discovery again. Configured attribute values appear as columns in the VMware VM inventory and as named read-only fields in Deep Scan. Reads fall back from customValue to value and VM summary, with only selected keys stored.

### Mapping to existing LanLens fields and device history

In the VMware tab, each custom attribute can optionally target an existing LanLens documentation field. Empty fields are populated by default; overwriting a nonempty value requires the explicit per-mapping option. The existing SYSID import remains separately protected and is selectable in the same dropdown. Network identities, credentials and CMDB object IDs are not writable through this mapping. Changes require a unique VM UUID and matching MAC. Discovery records new links, changed inventory fields, selected attribute changes (values redacted), and imported documentation fields in the device timeline; repeated unchanged scans do not add events. Historical changes from before this feature cannot be reconstructed.

### Automatic discovery schedule

Enable automatic VMware scans in Deep Scan → VMware. Configure the interval from 5 to 10,080 minutes (default 60, automatic scans disabled by default). The backend checks the persisted schedule each minute; it runs the same discovery workflow as the manual button. The interval is measured from the last scan attempt (including unsuccessful attempts) or the previous successful discovery for older installations. If there is no previous scan, the first automatic scan is due immediately. Manual and scheduled jobs share the discovery lock; overlapping scans are skipped. Disabled features and incomplete connections are not scanned. Settings persist across restarts.
