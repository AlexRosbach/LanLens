# i-doit HTTPS and application matching

## HTTPS (issue #141)

Use the actual HTTPS endpoint (for example `https://cmdb.example.test/idoit`) and the JSON-RPC path. Existing HTTP installations must migrate to HTTPS before syncing. API keys and Basic authentication must never be sent over HTTP. LanLens uses DNS validation and a pinned IP connection with TLS hostname verification and SNI. It does not follow redirects or disable certificate validation. For an internal CA, mount a trusted **combined CA bundle** containing public roots and your internal CA into the backend container read-only and set `SSL_CERT_FILE` to its absolute path. Restart the container and run Test connection. Do not mount private CA keys. Correct the server certificate chain, hostname or trust store if verification fails.

## Diagnose application matching

In Settings → CMDB/i-doit, save the connection settings and use **Test application matching** with a detected application title. This is read-only and reports title candidates, object IDs, the resolved type/catalog size, status filtering and incomplete pagination; it does not create any object. Compare with the existing Application object in i-doit. A non-empty matching result establishes lookup, not a write. After a manual sync, inspect `application_resolution_counts`, `application_lookup`, `application_save_counts` and any read-back warning. The application relation is written to `C__CATG__APPLICATION` on the target host with a numeric `application` object ID, per the [official category documentation](https://kb.i-doit.com/en/basics/categories/application.html). The catalog queries use the documented [`cmdb.objects.read`](https://knowledgebase.i-doit.com/en/i-doit-add-ons/api/methods/v1/cmdb.objects.html) and [`cmdb.object_types`](https://kb.i-doit.com/en/i-doit-add-ons/api/methods/v1/cmdb.object_types.html) methods. Match-only remains the default. Do not enable create-missing just to work around an incomplete lookup.
